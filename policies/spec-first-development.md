# 스펙 우선 개발 정책

## 목적

구현 전에 제품 동작, 범위, 검증 기준을 먼저 합의한다.

## 규칙

사용자가 구현, 세팅, 기능 추가, 리팩터링을 요청하면 관련 스펙을 먼저 확인한다.

관련 스펙이 없으면 구현을 시작하기 전에 새 스펙 이름과 구현 범위 초안을 제안한다.

사용자 결정이 필요한 항목이 있으면 질문을 먼저 정리한다.

사용자가 스펙 방향을 확인한 뒤 스펙 문서를 작성하거나 수정한다.

새 기능 스펙 파일 이름은 `YYYYMMDD-feature-name.md` 형식을 사용한다.

하나의 PR은 하나의 스펙 문서를 기준으로 진행한다.

PR 범위가 여러 스펙으로 나뉘면 구현 전에 PR 범위를 줄이거나 대표 스펙 하나로 정리한다.

스펙과 정책이 확정된 뒤 구현을 시작한다.

## 금지 사항

관련 스펙이 없는 상태에서 코드, 설정 파일, 패키지 설치, scaffold 생성을 시작하지 않는다.

사용자 확인 없이 기술 스택, 폴더 구조, 검증 명령을 확정하지 않는다.

하나의 PR에서 여러 새 기능 스펙을 동시에 만들지 않는다.

## 예외 처리

문서 오탈자 수정, 단순 조회, 상태 확인처럼 제품 동작이나 구현 구조에 영향을 주지 않는 작업은 관련 문서를 확인한 뒤 바로 수행할 수 있다.

긴급 수정처럼 구현을 먼저 해야 하는 경우에도 작업 완료 전 관련 스펙과 정책을 같은 작업 안에서 정리한다.
