# Create PR

## 작업 흐름

1. 현재 브랜치, working tree 상태, 최근 commit, diff를 확인한다.
2. 기억이 아니라 코드와 문서를 기준으로 변경 범위를 확인한다.
3. 가능한 경우 관련 테스트와 검증 명령을 실행한다.
4. 간결한 PR 제목과 본문을 작성한다.
5. 모든 PR 본문에 리뷰 필요 항목과 사용자 컨펌 필요 항목을 포함한다.
6. remote와 인증이 준비되어 있으면 브랜치를 push하고 PR을 생성한다.
7. PR URL, 검증 결과, 막힌 단계를 보고한다.

## PR 본문 필수 섹션

모든 PR 본문은 한국어로 작성한다.

모든 PR 본문에는 다음 한국어 섹션을 포함한다.

```md
## 요약

- 

## 검증

- 

## 리뷰 필요

- 

## 사용자 확인 필요

- 
```

`리뷰 필요`에는 리뷰어가 자세히 봐야 하는 코드 경로, 설계 선택, 위험한 동작, 테스트 공백, UX 세부사항을 적는다.

`사용자 확인 필요`에는 사용자의 확인이 필요한 제품 결정, 애매한 요구사항, 동작 tradeoff, 이름 선택, 범위 경계, release concern을 적는다.

필수 섹션에 넣을 항목이 없으면 해당 섹션에 `- 없음`을 적는다.

## PR 본문 스타일

본문은 짧고 구체적으로 작성한다.

구체적인 파일, 동작, 결정을 가리키는 bullet을 사용한다.

불확실한 내용은 요약에 숨기지 않는다.

불확실성, tradeoff, 가정은 `리뷰 필요` 또는 `사용자 확인 필요`에 적는다.

## 생성 규칙

commit 또는 push 전에 현재 브랜치를 확인한다.

사용자가 명시적으로 요청한 경우에만 `main` 또는 `master`에서 PR을 생성한다.

브랜치에 remote가 없으면 upstream branch를 설정해 push한다.

사용 가능한 경우 저장소의 기존 PR 도구 또는 `gh pr create`를 사용한다.

git repo, remote, 인증, CLI 도구가 없어 PR 생성이 막히면 제목과 본문 준비까지 진행하고 막힌 이유를 보고한다.
