# 작업 플로우

## 원칙

이 프로젝트는 스펙 주도 개발 방식으로 진행한다.

기능 구현 전에 반드시 관련 스펙과 정책을 먼저 확인한다.

관련 스펙이나 정책이 없거나 모호하면 구현보다 문서 작성을 먼저 한다.

스펙을 만드는 과정은 사용자와 티키타카하며 진행한다.

애매하거나 정확하지 않은 부분은 임의로 판단하지 않고 사용자에게 물어본 뒤 결론을 정리한다.

스펙 문서는 핵심만 간결하게 작성한다.

정책 문서는 핵심만 간결하게 작성한다.

큰 기능을 한 번에 구현하지 않는다.

## 기본 순서

1. `AGENTS.md` 확인
2. `specs/INDEX.md`에서 관련 스펙 확인
3. `policies/INDEX.md`에서 관련 정책 확인
4. 구현 범위 정리
5. 필요한 경우 사용자와 논의하며 스펙 또는 정책 작성
6. 스펙과 정책 확정
7. 작은 단위로 구현
8. 테스트 코드 작성
9. 검증 명령 실행
10. 로컬 앱 실행 또는 가능한 방식의 직접 확인
11. 문서와 코드 싱크 확인
12. 현재 브랜치 확인
13. 커밋, 푸시, PR 생성
14. 변경 내용 요약

## 스펙 작성

스펙 작성 중 애매한 요구사항, 불명확한 동작, 선택지가 있는 설계 결정은 사용자에게 질문한다.

질문과 답변을 통해 결론을 정리한 뒤 스펙에 반영한다.

스펙 파일 이름은 `YYYYMMDD-feature-name.md` 형식을 사용한다.

기능 스펙은 `specs/features/` 아래에 둔다.

예시는 `specs/features/20260709-agent-session-switching.md`와 같다.

하나의 PR은 하나의 스펙 문서를 기준으로 진행한다.

PR에서 새 기능 스펙이 필요하면 새 스펙 하나를 만들고 `specs/INDEX.md`에 등록한다.

PR에서 기존 스펙을 이어서 다루면 새 스펙을 추가하지 않고 기존 스펙 하나를 수정한다.

스펙은 구현에 필요한 핵심만 담는다.

스펙에는 중복 설명, 장식적인 배경 설명, 아직 결정되지 않은 세부 구현을 넣지 않는다.

## 스펙 우선 응답

사용자가 구현, 세팅, 기능 추가, 리팩터링을 요청했을 때 관련 스펙이 없으면 구현을 시작하지 않는다.

첫 응답에서는 관련 스펙 존재 여부를 확인하고, 새로 작성하거나 수정할 스펙 이름을 제안하고, 구현 범위 초안을 제시하고, 사용자 결정이 필요한 질문을 먼저 정리한다.

사용자가 스펙 방향을 확인하기 전에는 코드, 설정 파일, 패키지 설치, scaffold 생성을 수행하지 않는다.

## 정책 작성

정책은 구현 판단에 직접 필요한 규칙만 담는다.

정책에는 반복 설명, 과도한 예외 목록, 아직 적용할 대상이 없는 규칙을 넣지 않는다.

정책이 만들어지면 정책 인덱스에 등록한다.

## 구현과 테스트

스펙과 정책이 만들어지면 구현을 진행한다.

구현할 때는 테스트 코드를 함께 작성한다.

테스트가 실패하면 작업을 완료하지 않는다.

테스트를 실행할 수 없는 상태라면 실행하지 못한 이유를 작업 요약에 남긴다.

## 로컬 직접 확인

테스트가 통과하면 로컬에서 앱을 직접 실행해 주요 흐름이 동작하는지 확인한다.

데스크탑 앱은 가능한 경우 Tauri dev app을 실행해 화면과 상호작용을 확인한다.

로컬 실행이나 화면 확인이 불가능한 환경이면 이유와 대신 수행한 검증을 작업 요약에 남긴다.

## 브랜치와 PR

구현과 검증이 끝나면 현재 브랜치를 확인한다.

변경 내용을 커밋하고 원격 브랜치에 푸시한다.

PR을 생성한다.

git repo, remote, 인증, PR 도구가 준비되지 않은 경우에는 가능한 단계까지 수행하고 막힌 이유를 작업 요약에 남긴다.

검증이 끝난 상태를 작업 완료로 간주하지 않는다.

최종 응답 전에 `AGENTS.md`의 작업 완료 규칙과 이 문서의 작업 완료 보고 항목을 체크리스트로 다시 확인한다.

## 구현 범위 관리

요청받은 작업 범위를 벗어난 기능을 임의로 추가하지 않는다.

새로운 기능 아이디어가 떠오르면 바로 구현하지 말고 spec 또는 task 문서에 기록한다.

MVP 이전에는 완성형 IDE 기능보다 agent context switching 경험을 우선한다.

## 작업 완료 보고

작업 완료 후 다음 항목을 포함해 보고한다.

* 변경한 파일
* 구현한 내용
* 실행한 검증 명령
* 로컬 직접 확인 결과
* 문서와 코드 싱크 확인 결과
* 브랜치, 커밋, 푸시, PR 상태
* 남은 한계
* 다음에 이어서 할 작업
